# ИИ-помощник покупателя (Avito Start × ЮФУ)

Помощник получает диалог покупателя («Нужен стол не шире метра, кресло и лампа.
Таганрог. До 15 000 ₽ за всё») и возвращает **один JSON** с 1–3 комплектами из
каталога, уточняющими вопросами или объяснением, почему подходящего варианта нет.

* каталог, подбор, цены и объяснения — **локальный код, 0 токенов модели**;
* языковая модель вызывается **только** для извлечения условий, которые лексикон
  не понял, и в неё **никогда не передаётся каталог**;
* текст объявления (`description`) не влияет на ответ: это данные, а не
  инструкции (★ защита от промпт-инъекций).

---

## Быстрый старт

```sh
# 1. зависимости (единственная внешняя — jsonschema, остальное stdlib)
python -m pip install -r requirements.txt

# 2. ключ модели: только в .env, он в .gitignore и в репозиторий не попадает
cp .env.example .env        # затем впишите LLM_API_KEY, выданный организатором

# 3. запуск ровно так, как в контракте
./run --catalog /absolute/path/catalog.json < request.json > response.json
```

Требуется Python 3.10+ (проверено на 3.15) и bash для `./run` — файл должен быть
исполняемым (`git update-index --chmod=+x run`, если он потерял бит при переносе).
Без bash то же самое запускается напрямую:

```sh
python -m app.main --catalog data/catalog.json < examples/01-selection/request.json
```

### Примеры из условия

```sh
python -m app.main --catalog data/catalog.json < examples/01-selection/request.json
python -m app.main --catalog data/catalog.json < examples/02-clarification/request.json
```

### Свой каталог без категорий

Записи в формате собственного каталога автоматически включают поиск по
названиям. Флаг `--text-search` позволяет явно выбрать этот режим, в том
числе для пустого каталога внутри `products` или `listings`.

```sh
./run --catalog products.json < request.json
python web/serve.py --catalog products.json --offline
```

Файл содержит массив товаров или объект с массивом `products` либо
`listings`. Структура записи, например:

```json
[
  {"id": "r-1", "title": "Железная решётка", "price_rub": 900, "city_id": "tomsk", "city_name": "Томск"},
  {"id": "r-2", "title": "Железная решётка усиленная", "price_rub": 1500, "city_id": "tomsk", "city_name": "Томск"},
  {"id": "m-1", "title": "Железная метёлка для решёток", "price_rub": 300, "city_id": "tomsk", "city_name": "Томск"}
]
```

Используйте одинаковый идентификатор города во всех его записях. Например,
для `"city": "Томск"` идентификатором будет `Томск`. Если в файле вместо этого
используется `"city_id": "tomsk"`, поле `city_name` позволяет искать город по
русскому названию. Дополнительные названия города можно указать в `city_aliases`.
Нужны уникальный строковый `id`, название, город и
положительная целая цена в рублях. `category` и `description` для поиска не нужны.
Текстовый поиск учитывает отдельные названия из `aliases` и `keywords`,
в том числе внутри объектов и массивов. Для уточнения названия используются
собственные свойства товара из `attributes`: материал, цвет, бренд и модель.

Пример запроса: `{"messages":[{"role":"user","text":"Покажи три варианта железных решёток в Томске до 2000 ₽"}]}`.
Каждый вариант содержит одно объявление. Помощник вернёт до трёх подходящих
вариантов, от более дешёвых к более дорогим. «Метёлка для решёток» подходит
по запросу о метёлке, а «железная балка» и «железная палка» дают разные результаты.

Индекс строится по переданному файлу. Он сопоставляет слова целиком и учитывает
распространённые русские словоформы. При неполных условиях помощник уточняет
город, бюджет или товар. Для описания вроде «что-нибудь, чтобы закрыть
отверстие» модель может определить товар до уточнения города и бюджета.
Если название уже распознано, но точному поиску мешают слова вроде «вкусный»,
модель может подтвердить, что их можно опустить. Название и распознанные
свойства остаются в поиске. На запрос приходится до одного вызова модели.
Предложенное название проверяется в текущем каталоге. Режим рассчитан на альтернативы одного
товара. Структурированные ограничения и комплекты из нескольких категорий
поддерживает штатный режим ТЗ.

### Каталог по URL

В `--catalog` можно передать прямой URL JSON-файла. Для GitHub используйте
адрес из кнопки **Raw**. CLI читает каталог заново на каждый запрос и добавляет
к URL уникальный параметр `t`, чтобы обойти кэш. Веб-демо использует тот же
источник для подбора и карточек.

```sh
./run --catalog 'https://raw.githubusercontent.com/OWNER/REPO/BRANCH/data/catalog.json' < request.json
```

## Сетевые зависимости и место использования модели

Модель `google/gemma-4-31B-it` доступна через шлюз организаторов
(`LLM_API.md`). При выборе каталога по URL выполняется отдельный HTTP-запрос
за JSON с таймаутом 5 секунд. Подбор выполняется локально в обоих случаях.

Параметры подключения читаются из окружения, значения можно менять при финальной
проверке:

| Переменная | Назначение |
|---|---|
| `LLM_BASE_URL` | адрес шлюза (только `https`, либо `http` на loopback для тестов) |
| `LLM_MODEL` | имя модели |
| `LLM_API_KEY` | ключ команды; **только** из `.env`/окружения |
| `LLM_USER_AGENT` | имя клиента (без него `workers.dev` отвечает `403 error code: 1010`) |

**Где используется модель.** Сетевые вызовы Gemma выполняет `complete()` в
`app/llm/client.py`. В штатном режиме запрос формируют при разборе истории в
`app/nlp/merge.py`, а в режиме `--text-search` — в `app/llm/product.py`.
В модель уходит системный промпт и описание товара из реплик покупателя.
Что **не** уходит: каталог, объявления, описания, ID, цены.

В штатном режиме модель получает описание товара и возвращает только
`categories`. Если по назначению можно понять, какой товар ищут, описание
обрабатывается до уточнения города и бюджета. Город и бюджет извлекаются локально.
В режиме `--text-search` клиент извлекает короткое название для локального
поиска. Каталог и описания объявлений остаются на машине в обоих режимах.

Что считается локально (0 токенов): разбор города/категорий/чисел/границ,
бинарный поиск по индексу, подбор комплектов, объяснения, `no_match`.
Подробности и цифры — [docs/TOKEN_BUDGET.md](docs/TOKEN_BUDGET.md).

### Настройки офлайн-режима и кэша

| Переменная | Эффект |
|---|---|
| `ASSISTANT_OFFLINE=1` | модель не вызывается вообще; работает только лексикон |
| `ASSISTANT_NO_CACHE=1` | отключить файловые кэши (индекс и разборы) |
| `ASSISTANT_CACHE_DIR=…` | перенести кэши (используется тестами) |

В офлайн-режиме помощник полностью работоспособен: корректные запросы
обслуживаются лексиконом, а неоднозначные дают `clarify`. Именно так работают
тесты подбора и нагрузочный стенд. Для работы без сети укажите локальный файл
каталога и `ASSISTANT_OFFLINE=1`.

## Контракт вызова

```sh
./run --catalog /absolute/path/catalog.json < request.json > response.json
```

Один вызов = один процесс = один запрос. Вход — один JSON-объект до EOF,
выход — ровно один JSON-объект в stdout (логи только в stderr).

| Статус | Что означает |
|---|---|
| `ok` | 1–3 варианта комплекта в бюджете покупателя |
| `clarify` | не хватает обязательных условий; в ответе вопросы по каждому |
| `no_match` | условия полны, но подходящего комплекта нет; в ответе объяснение |

Коды выхода:

| Код | Когда |
|---:|---|
| 0 | ответ отдан (любой из трёх статусов) |
| 2 | нарушение контракта входа или аргументов |
| 3 | каталог не читается / не проходит схему |
| 4 | ошибка конфигурации |
| 5 | внутренний сбой, включая недоступность модели |

`no_match` для технических ошибок не используется никогда: сбой сервиса — это
exit 5, пустой stdout и объяснение в stderr.

## Запуск демо

Демо — это **опциональная обёртка** над бэкендом: подбор выполняет ровно тот же
`./run` (`python -m app.main`), а скрипт и страница только вызывают его и
показывают ответ. Весь код демо — это `demo.sh` в корне и `web/`; бэкенд не
меняется.

### Консольная демонстрация

> **Важно: один раз выставить бит исполнения** (в Linux-клоне или на сервере, где
> будет запуск). Без этого скрипт остановится с подсказкой, а не выполнится:
>
> ```sh
> chmod +x run demo.sh
> ```
>
> Для Windows запускайте через `bash demo.sh` (Git Bash / MSYS2 / WSL). Этот
> путь проверен: скрипт сам находит рабочий интерпретатор, потому что `python3`
> и `python` на Windows часто оказываются заглушкой Microsoft Store — они есть
> в PATH, но при запуске падают.

```sh
bash demo.sh
```

Скрипт проверяет, что `run` существует и исполняемый, прогоняет оба открытых
примера из `examples/` и запрос с попыткой инъекции, печатая статус, ID товаров
и итоговую сумму. Суммы сверяются с `data/catalog.json`, поэтому «Защита от
инъекции: пройдена» — это результат проверки, а не готовая фраза.

Интерпретатор скрипт подбирает сам (проверяет, что кандидат действительно
исполнил код) и передаёт найденный бэкенду через `PYTHON`, так что демонстрация
и `./run` гарантированно работают одним python. Задать свой можно явно:

```sh
PYTHON=python3.12 bash demo.sh
```

Сами проверки встроены в `demo.sh` (heredoc-и) и утверждают статус `ok`,
непустой `options`, наличие `budget_rub` в вопросах, а также совпадение каждой
суммы с ценами из каталога. Пустой список вариантов при статусе `ok` считается
провалом — проверять там нечего.

### Веб-демо

```sh
py -3.14 web/serve.py
```

Затем откройте <http://127.0.0.1:8000/>. Сервер на стандартной библиотеке
(`http.server`), зависимостей нет.

| Эндпоинт | Назначение |
|---|---|
| `POST /api/answer` | тело `{"messages": […]}` → ответ бэкенда как есть (`ok` / `clarify` / `no_match`) |
| `POST /api/answer?include=cards` | подбор и карточки из одного снимка каталога |
| `GET /api/listings?ids=a,b,c` | карточки товаров для интерфейса (без поля `description`) |
| `GET /`, `/app.js`, `/style.css` | статика демо |

Флаги: `--port` (по умолчанию `8000`, `0` — свободный), `--host`, `--catalog` (путь или URL),
`--offline` (только добавляет `ASSISTANT_OFFLINE=1`, окружение не перетирает).
Метрики вызова модели уходят в заголовки ответа (`X-Model-Calls`,
`X-Model-Tokens`, `X-Elapsed-Ms`, `X-Model-Mode`), чтобы не менять контракт;
подробности — в [web/README.md](web/README.md).

**Основной интерфейс системы — консольный `./run`** (как требует ТЗ). Веб-демо
существует только для показа: если бэкенд завершился с кодом 5 (сбой сервиса),
страница показывает «Сервис временно недоступен» и не подменяет сбой статусом
`no_match`.

## Как это устроено

```
app/
  main.py            точка входа: stdin → пайплайн → stdout, коды выхода
  pipeline.py        порядок правил: сначала clarify, потом подбор
  contract/          проверка запроса и самопроверка ответа
  nlp/               lexicon-first разбор: числа, лексикон, слияние истории, кэш
  catalog/           индекс, бинарный поиск, подбор, объяснения
  llm/               клиент модели (лимиты, 429, ошибки)
  prompt_safety.py   ★ защита от инъекций и диагностика каталога
bench/load.py        нагрузочный стенд: задержки, пропускная способность, токены
bench/acceptance.py  репетиция автопроверки §1–§4: генератор каталогов, Oracle, диалоги
bench/accuracy.py    метрика точности извлечения: эталон 237 реплик, веса ошибок, baseline
docs/                ALGORITHMS.md (все алгоритмы + «На защите»), ACCURACY.md, TOKEN_BUDGET.md
tests/               700+ тестов, сеть не требуется
```

Ключевые решения:

* **Индекс строится от содержимого каталога** (`sha256`), а не от пути: подмена
  каталога организаторами автоматически инвалидирует кэш.
* **Бинарный поиск** по отсортированным значениям характеристик вместо перебора;
  подбор — DFS с отсечением по суффиксным минимумам цен.
* **Отсутствующая характеристика не считается подходящей**: если покупатель
  просил «не шире 100 см», стол без указанной ширины не подтверждает условие.
* **`False` — это данные**, а не отсутствие значения: «кресло без регулировки»
  фильтруется отдельной выборкой, а не проверкой truthiness.
* **Слово в роли места — не товар**: «посветить над столом» даёт лампу, а не стол;
  нечёткое совпадение с прилагательным («работой» → «рабочий») товар не создаёт,
  а опечатка существительного («стлл» → «стол») — создаёт.
* **★ Инъекции**: каталог в модель не передаётся; `description` не читает ни один
  модуль подбора (проверяется тестом по исходникам); попытки манипуляции видны в
  stderr, но не меняют ответ.

Полное описание каждой ключевой функции и сценарий защиты —
[docs/ALGORITHMS.md](docs/ALGORITHMS.md).

## Тесты и замеры

```sh
python -m unittest discover -s tests -t .   # 700+ тестов, ~60 с, без сети
python bench/load.py                        # задержки, пропускная способность, токены
python bench/load.py --json                 # те же метрики в JSON
python bench/acceptance.py                  # репетиция автопроверки: каталоги, Oracle, диалоги
python bench/acceptance.py --cases 60 --seed 7   # шире и на другом наборе данных
python bench/accuracy.py                    # точность извлечения условий на эталоне
python bench/accuracy.py --check            # упасть при регрессе точности
```

`bench/acceptance.py` — независимый стенд: сам генерирует валидные каталоги §2,
сам формулирует запросы по §2.2 и своим перебором решает, что обязано быть в
ответе. Он не использует код подбора, поэтому ловит расхождения, которые
«наши» тесты пропускают.

`bench/accuracy.py` — второй, дополняющий стенд: 237 реплик, размеченных по
смыслу (§2), сравнение по каждому полю (`city_id`, `budget_rub`, `categories`,
`width`, `temperature`, `adjustable`) и по статусу ответа, с весами ошибок по
политике «лучше переспросить, чем понять неверно». Текущий результат: **237 из
237 полностью верных, безопасность 1.0000, опасных ошибок 0**; цифры заморожены
в `bench/golden/baseline.json`, регресс роняет `tests/test_accuracy.py`.
Методика, веса и честные границы измерения — [docs/ACCURACY.md](docs/ACCURACY.md).

Тесты проверяют не только «работает», но и контракт: коды выхода, отсутствие
лишних полей, устойчивость к «отравленному» каталогу, лимиты шлюза (на локальном
HTTP-сервере), соответствие документации коду.

Ориентиры на каталоге организаторов (111 объявлений): подбор — 0,04 мс p50,
полный `./run` с запуском интерпретатора — 166 мс p50 при лимите 120 с,
89 % запросов в нагрузочном прогоне обслуживаются без вызова модели. В
сквозном замере с короткой схемой два вызова заняли 108 и 110 токенов.

## Безопасность ключа

* ключ живёт **только** в `.env` (или переменной окружения) и никогда не в коде;
* `.env` в `.gitignore`, в репозитории есть только `.env.example` с пустым значением;
* ключ вырезается из любого текста, который может попасть в stderr
  (`llm.client.redact`), а в логи печатается только его длина;
* редиректы при вызове шлюза запрещены: ключ не уйдёт на чужой хост.
