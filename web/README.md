# Демо-сайт «ИИ-помощник покупателя»

Веб-интерфейс к готовому бэкенду подбора мебели. Сайт ничего не подбирает сам:
он вызывает `python -m app.main` отдельным процессом, печатает его ответ и
показывает карточки товаров из источника, указанного в `--catalog`.

## Запуск

```powershell
py -3.14 web/serve.py
```

Открыть <http://127.0.0.1:8000/>.

> На этой машине `python` в PATH — заглушка Microsoft Store, поэтому в примерах
> `py -3.14`. Внутри сервера путь к интерпретатору берётся из `sys.executable`,
> так что жёсткого `python3` нигде нет.

### Флаги

| Флаг | По умолчанию | Зачем |
|---|---|---|
| `--host` | `127.0.0.1` | наружу не светим; `0.0.0.0` только осознанно |
| `--port` | `8000` | `0` — любой свободный порт (нужно `tests/test_web.py`) |
| `--catalog` | `data/catalog.json` | путь или прямой HTTP(S)-URL JSON для бэкенда и карточек |
| `--text-search` | автоопределение | явно включить поиск по названиям и псевдонимам, включая пустые `products` или `listings` |
| `--offline` | выключен | выставляет `ASSISTANT_OFFLINE=1` процессу бэкенда |

`--offline` **добавляет** переменную, а не перетирает её: если оператор сам
выставил `ASSISTANT_OFFLINE=1`, сервер это уважает. По умолчанию режим обычный —
на защите видно вызов модели.

## Файлы

| Файл | Что внутри |
|---|---|
| `index.html` | разметка: чат, панель вариантов, 4 примера запросов |
| `style.css` | тема на CSS-переменных, две колонки → одна на узком экране |
| `app.js` | история диалога, `AbortController` на 120 с, рендер трёх статусов |
| `serve.py` | HTTP-шлюз: статика, `/api/answer`, `/api/listings`, метрики |

Проверки шлюза живут в `tests/test_web.py` рядом с остальными тестами
репозитория, а не внутри `web/`.

## API

### `POST /api/answer`

Тело: `{"messages": [{"role": "user", "text": "…"}]}` — 1..20 сообщений,
роли `user`/`assistant` строго чередуются, первая и последняя — `user`,
у сообщения ровно два поля.

Ответ — **тело бэкенда как есть**, один из трёх статусов:

```json
{"status":"ok","options":[{"listing_ids":["…"],"total_rub":4200,"explanation":"…"}]}
{"status":"clarify","questions":[{"field":"budget_rub","text":"…"}]}
{"status":"no_match","message":"…"}
```

Метрики уходят **в заголовки**, чтобы не менять контракт:

| Заголовок | Значение |
|---|---|
| `X-Model-Calls` | число запросов к модели (повтор после 429 входит в тот же запрос) |
| `X-Model-Tokens` | суммарно токенов, если шлюз сообщил расход |
| `X-Elapsed-Ms` | время ответа бэкенда |
| `X-Model-Elapsed-Ms` | время ожидания шлюза модели с учётом повторной попытки, если она была |
| `X-Model-Mode` | `offline` при флаге `--offline`, иначе `on-demand` |
| `X-Model-Unavailable` | `1`, если бэкенд сообщил, что модель недоступна |
| `X-Model-Reused` | `1`, если ответ использовал предыдущий разбор товара и нового вызова модели не было |
| `X-Catalog` | `ok` или `bad` |

`X-Model-Mode` отвечает **сервер** — по флагу `--offline`, а не по строкам лога
бэкенда: сообщение «модель недоступна» одинаково и при `--offline`, и при
отсутствующем ключе, поэтому по нему режим отличить нельзя.

Коды: `200` — ответ; `400` — клиент прислал не по контракту; `411`/`413` — тело;
`500` — не удалось запустить бэкенд; `502` — бэкенд упал (последняя строка его
stderr уходит в `{"error": …}`); `504` — бэкенд не ответил за 125 с.
**Сбой сервиса никогда не превращается в `no_match`.**

### `POST /api/answer?include=cards`

Тот же запрос возвращает `{"answer": …, "items": […]}`. Подбор и карточки
используют один снимок JSON на запрос. Если получен заголовок
`X-Dialogue-Token`, браузер передаёт его с продолжением этого же диалога.
Сервер сверяет историю и может использовать предыдущий разбор товара после
уточнения города или бюджета. Разбор хранится в памяти сервера.

### `GET /api/listings?ids=a,b,c`

Карточки для интерфейса. Белый список полей:
`id, category, category_name, title, price_rub, city_id, city_name, attributes`.
Поля `description` в ответе нет вообще — по условиям кейса описания не участвуют
в подборе. Неизвестные id попадают в `missing`.

### Служебные маршруты

| Маршрут | Ответ |
|---|---|
| `GET /robots.txt` | `200`, `User-agent: * / Disallow: /` — демо закрыто от индексации |
| `GET /favicon.ico` | `204` — файла нет, но 404 не шумит в логах и в консоли |

## Проверка

```powershell
py -3.14 -m unittest tests.test_web
# или весь набор: py -3.14 -m unittest discover -s tests -t .
```

Тесты поднимают сервер на свободном порту и проверяют HTTP-контракт,
единый снимок каталога, продолжение диалога и обработку сбоев бэкенда.

Ручной сценарий демо:

1. «Стол, кресло и лампа. Таганрог. До 15000.» → `ok`, 1–3 варианта.
2. «Новый диалог» → «Нужен стол в Таганроге» → `clarify` про бюджет.
3. Ответить «15 тысяч» в том же диалоге → `ok`.
4. «Новый диалог» → «Нужен стол в Таганроге до 100 ₽» → `no_match`.
5. Остановить сервер и нажать «Подобрать» → блок «Сервис недоступен», не падение.

## Честные оговорки

- **Пункты 2–4 нужно начинать с «Нового диалога».** Условия переносятся между
  репликами: после подбора с бюджетом вопрос про бюджет уже не задаётся — это
  поведение ядра, а не интерфейса.
- **Сумма требует единицы валюты.** «до 100» без `₽`/`руб` читается как
  отсутствующий бюджет и даёт `clarify`; «до 100 ₽» — `no_match`.
- **Без ключа модели** четвёртый пример («деревяшка») уйдёт в `clarify`: лексикон
  не знает такого слова, а модель недоступна. Это штатный офлайн-режим.

## Безопасность

- Любой текст с сервера выводится только через `textContent`. `innerHTML`,
  `insertAdjacentHTML`, `eval`, `new Function` не используются.
- Статика раздаётся по белому списку `STATIC_FILES`: URL не превращается в путь
  файловой системы, поэтому `../app/main.py` и `../../.env` дают `404`.
- Заголовки: `CSP default-src 'self'`, `nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: no-referrer`.
- Ключ модели хранится на сервере.
- Сервер выполняет локальные подборы параллельно. Вызовы шлюза модели из
  дочерних процессов одного сервера выполняются по одному.
