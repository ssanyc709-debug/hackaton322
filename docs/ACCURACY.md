# Точность извлечения условий

Ответ на вопрос жюри и ментора «какая у вас точность». Здесь описано, **что**
измеряется, **на чём**, **как считается** и **где предел измерения** — чтобы
цифру можно было проверить, а не принять на веру.

Эталонный набор — **237 размеченных реплик**, полностью верных
**237 (100 %)**, безопасность **1.0000**, опасных ошибок **0**. Ухудшение
роняет `tests/test_accuracy.py`. Ниже — как это получилось и почему одним числом
дело не ограничивается.

## Зачем отдельная метрика

Юнит-тесты доказывают, что правило работает на **известном** примере. Они не
отвечают на вопрос «какая точность» и не замечают, что новое правило испортило
соседнее: 715 тестов зелёные, а конкретная живая фраза разбирается неверно.
Метрика закрывает именно этот зазор:

* разметка написана **по смыслу фразы и ТЗ §2**, а не по выводу парсера;
* сравнивается каждое поле отдельно, поэтому видно, **какое** условие теряется;
* у ошибки есть **цена** (см. «Веса»), поэтому «стало на 2 % хуже» превращается
  в «покупатель получил `ok`, хотя условие не понято»;
* цифры заморожены в `bench/golden/baseline.json`, и тест падает при регрессе.

## Что измеряется

Два слоя, потому что продукт отвечает не только «условия разобраны», но и
«ответ по §4 правильный».

### 1. Извлечение (лексикон, 0 токенов модели)

Сравниваются шесть полей каждой реплики:

| Поле | Что значит | Пример |
|---|---|---|
| `city` | город из §2 или `null` | «в Таганроге» → `taganrog` |
| `budget` | бюджет в рублях (верхний предел) | «до 15 000 ₽» → `15000` |
| `categories` | набор товаров (множество) | «стол и кресло» → `table, chair` |
| `width` | диапазон ширины стола, см | «не шире 100 см» → `≤ 100` |
| `temperature` | диапазон температуры лампы, K | «4000 K» → `= 4000` |
| `adjustable` | регулировка высоты: да/нет/неизвестно | «без регулировки» → `false` |

Для каждой реплики фиксируется **вид расхождения**:

* `false_negative` — условие названо, но потеряно («стол» выпал из набора);
* `false_positive` — условие выдумано (бюджет там, где его не называли);
* `wrong_value` — условие понято неверно (не тот город, не та граница).

Включительность границы — часть условия: `≤ 100` и `< 100` считаются разными.

### 2. Ответ (сквозной прогон по §4)

Для реплик со статусом в разметке проверяется сам ответ контракта:

* `ok` / `clarify` / `no_match` — совпал ли статус;
* состав вопросов при `clarify` — не спросили ли лишнего (`overask`) и не забыли
  ли обязательное (`underask`).

Ошибки статуса взвешены дороже ошибок полей: неверный ответ дороже неверного
слота, потому что покупатель видит именно ответ.

## Веса ошибок

Политика продукта сформулирована ментором: **«лучше переспросить, чем понять
неверно»**. Поэтому ошибки не равны:

| Вес | Ошибка | Что произошло |
|---|---|---|
| 5 | `wrong_ok` | выдали `ok`, хотя условие не понято |
| 3 | `wrong_value` | поняли условие неверно (город, число, граница) |
| 3 | `false_negative` | потеряли названное условие |
| 2 | `wrong_no_match` | отсекли всё, хотя подходящие варианты есть |
| 2 | `underask` | не спросили то, без чего нельзя подбирать |
| 1 | `false_positive` | выдумали условие, которого не было |
| 1 | `false_clarify` | переспросили, хотя всё было известно |
| 1 | `overask` | спросили лишнее при `clarify` |

`безопасность = 1 − Σ весов / (5 · N)` — доля штрафа от максимума, где `N` —
число реплик. Единица означает «ни одной ошибки ни в одной реплике». «Опасными»
считаются ошибки с весом ≥ 3: из-за них покупатель получил неверный ответ.

## Набор

`bench/golden/extraction.jsonl` — одна реплика в строке, 237 строк, 9 блоков:

| Блок | Реплик | Что проверяет |
|---|---|---|
| `width` | 34 | все формы §2.2, ниша/проём, метры, «ширина 100, 15000» |
| `budget` | 30 | «до», «не дороже», «15к», «т.р.», падежи, «с половиной» |
| `city` | 20 | падежи, «Ростов-на-Дону», опечатки, город вне справочника |
| `categories` | 28 | наборы, «без лампы», «только стол», синонимы |
| `temperature` | 14 | «4000 K», «к», кельвины, диапазоны |
| `adjustable` | 10 | «с регулировкой», «нерегулируемое», «не важна» |
| `mixed` | 25 | несколько условий сразу + статус ответа |
| `hard` | 60 | живая речь, ложные совпадения, количества и неоднозначные диапазоны |
| `noop` | 16 | «спасибо», «лады», мусор — условий быть не должно |

Разметка делалась **до** прогона парсера. Правила, по которым строка считается
верной:

* значение берётся из смысла фразы и §2, а не из того, что вернул код;
* если фраза допускает два прочтения («Стол 142» — ширина или цена?), правильный
  ответ — **`null`**: по политике «лучше переспросить» условие не угадывается;
* `clarify` может спрашивать только `city_id`, `budget_rub` и `categories`.
  Неоднозначное необязательное ограничение остаётся пустым. Например,
  «лампа от 3000 до 5000» без контекста не задаёт температуру. Если бюджет
  неизвестен, помощник уточняет только бюджет при известных городе и категории;
* «стол без лампы» — это набор `{table}`: лампа названа, но снята;
* «бюджет — верхний предел» (§3), поэтому «от 15 000 до 20 000» → `20000`.

## Как это запускать

```bash
python bench/accuracy.py                    # отчёт: поля, блоки, статусы, ошибки
python bench/accuracy.py --block hard       # только живая речь
python bench/accuracy.py --errors 40        # больше ошибок в отчёте
python bench/accuracy.py --json             # машинный отчёт
python bench/accuracy.py --check            # упасть, если хуже baseline
python bench/accuracy.py --update-baseline  # заморозить новые цифры (осознанно)
python -m unittest tests.test_accuracy      # то же в общем прогоне
```

Модель не вызывается: стенд проверяет лексикон, то есть работает за доли секунды
и не тратит токены.

## Результат и что он показал

| Шаг | Реплик | Полностью верных | Что нашлось |
|---|---|---|---|
| первый прогон (базовые блоки) | 173 | 166 (96.0 %) | 9 расхождений: 5 настоящих багов, 2 мои ошибки разметки, 2 спорных случая |
| после исправлений | 173 | 173 (100 %) | — |
| добавлен блок живой речи | 228 | 226 (99.1 %) | 2 бага: «чтобы регулировалось по высоте», «бюджет на стол и кресло» |
| после исправлений | 228 | 228 (100 %) | безопасность 1.0000, опасных ошибок 0 |
| после аудита угадываний | 237 | 237 (100 %) | 9 новых реплик, 27 сквозных проверок статуса, безопасность 1.0000 |

Найденные метрикой баги (все исправлены и закреплены тестами):

1. «Стол 80-100 см» читалось как «ровно 100» — дефисный диапазон не сводился.
2. «лампа 3000-4000 K» давало бюджет 3000 и температуру 4000.
3. «до 20 т.р.» давало бюджет **20 ₽** (сокращение «т.р.» не распознавалось).
4. «нерегулируемое кресло» давало `adjustable = null` вместо `false`.
5. «сантиметров 90 в ширину» теряло ширину (единица перед числом).
6. «3-4 тысячи кельвинов» давало диапазон 3..4000 K.
7. «чтобы регулировалось по высоте» не включало регулировку.
8. «бюджет 20 000 ₽ на стол и кресло» теряло стол (предлог считался местом).

Два случая из первого прогона остались как **зафиксированное поведение**, а не
баги:

* «Таганрог или Азов» → берётся последний город: §3 требует **один** город,
  мульти-город сознательно вне области (`docs/QA-ERRORS.md`);
* «До 900» → помощник переспрашивает сумму. «Бюджет до 900» задаёт
  потолок 900 ₽ благодаря явному денежному слову.

## Предел измерения — честно

* Набор написан командой. Он не заменяет независимую разметку ментора, зато
  воспроизводим и лежит в репозитории.
* Точность 100 % относится к 237 репликам этого набора.
* Статусы проверяются на 27 репликах с разметкой ответа из блоков `mixed` и `hard`.
* Автопроверка `bench/acceptance.py` (60 дел, независимый oracle §4) остаётся
  главным доказательством корректности; метрика её **не** заменяет, они про
  разное: acceptance — «ответ верный», accuracy — «все ли условия разобраны».
  Автопроверка использует фразы §2.2, ручной каталог ментора — живую речь;
  именно эту разницу и закрывают блоки `hard` и веса ошибок.
* Метрика не измеряет формулировки ответа, порядок вариантов и работу модели:
  модель в стенде не вызывается.

## Как добавить реплику

1. Взять фразу **из ручного каталога ментора или из живого диалога**, не из кода.
2. Разметить по смыслу (см. правила выше) и дописать строку в
   `bench/golden/extraction.jsonl`: все ключи обязательны, `id` уникален.
3. Прогнать `python bench/accuracy.py --block <блок> --errors 40`.
4. Если код ошибся — сначала понять, чей это баг: кода или разметки. Ошибка
   разметки правится в наборе, ошибка кода — в коде, и тогда добавляется
   юнит-тест на конкретное правило.
5. Когда все реплики разобраны верно (или расхождения осознанно приняты), обновить
   baseline: `python bench/accuracy.py --update-baseline`.

Чтобы метрика не превратилась в «подгонку под набор», новые реплики пишутся
**до** прогона парсера по ним. Блок `hard` так и появился: 25 реплик живой речи,
первый прогон — 99.1 %, два бага, исправление, 100 %.
