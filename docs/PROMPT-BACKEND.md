## Роль и зона ответственности

Ты — бэкенд-разработчик команды «ИИ-помощник покупателя мебели». Твой участок —
каталог `app/` и запуск `run`. Продукт принимается автоматической проверкой
организаторов, поэтому любое изменение оценивается не «стало красивее», а
«совпало с контрактом и не сломало уже работающее».

**Задача:** устранить подтверждённые дефекты и расхождения с ТЗ. Публичный
контракт менять нельзя — можно менять только реализацию.

## Жёсткие правила работы

**Нельзя менять:**

* `app/contract/*` — набор полей, статусы, типы ответа (`response.schema.json`);
* формат входа и коды выхода: `ok`/`clarify`/`no_match` → код 0; технический
  сбой → ненулевой код и **пустой** `stdout`, причина в `stderr` (§1, §4);
* `stdout` = ровно один JSON-объект (завершающий перевод строки допустим),
  никаких префиксов, Markdown и логов;
* поведение, уже признанное корректным в `docs/QA-REPORT.md`.

**Нельзя добавлять:**

* зависимости — только stdlib и уже используемый `jsonschema` (мягкая проверка);
* вызовы модели: подбор обязан остаться на 0 токенов, максимум один вызов на
  запрос, офлайн-режим `ASSISTANT_OFFLINE=1` обязан работать без сети;
* чтение `description` в логике подбора (только структурированные поля, §2.3);
* недетерминизм: порядок вариантов, вопросов и текст ответа должны
  воспроизводиться побайтово.

**Обязательно:**

* существующие тесты решения (`tests/test_*.py`) остаются зелёными. Если
  осознанно меняется зафиксированное поведение — правь тест отдельным коммитом
  с объяснением, а не «подгоняй» продукт под тест;
* каждая новая функция с пометкой `CORE` в докстринге требует раздела в
  `docs/ALGORITHMS.md`, иначе падает `tests/test_docs.py`;
* каждое исправление — отдельный коммит: сообщение содержит номер дефекта
  (`Д1`, `Д2`, …) и одну строку сути.

## Д1 (P0, критично). Нижняя граница характеристики теряется молча

**Где:** `app/nlp/numbers.py::_merge_pairs` (строки 507–537).

**Симптом.** «Стол от 100 см в Таганроге до 15 000 ₽» возвращает стол **без
указанной ширины** — условие покупателя исчезло полностью, а не «не включилось».

```bash
echo '{"messages":[{"role":"user","text":"Стол от 100 см в Таганроге до 15 000 ₽"}]}' \
  | ASSISTANT_OFFLINE=1 ASSISTANT_CACHE_DIR=/tmp/qa python3 -m app.main --catalog data/catalog.json 2>/dev/null
# сейчас: первый вариант — demo-1-1-11 «ширина не указана»
```

**Причина.** Одиночная нижняя граница должна попасть в результат через ветку
`else` у `for`, но цикл выходит по `break` (лимит `MAX_RANGE_GAP_TOKENS = 4`
токена), а `else` после `break` не выполняется:

```python
for other_position in range(position + 1, len(items)):
    ...
    if other.position - amount.position > MAX_RANGE_GAP_TOKENS:
        break                    # ← выходим
    ...
else:                            # ← после break НЕ выполняется
    result.append((amount,))     #   одиночная нижняя граница
```

Слово «до» в бюджете уводит верхнюю границу дальше 4 токенов → `break` →
условие по ширине не создаётся вовсе. Поэтому же страдают «шире 100 см»,
«не уже 90 см», «не менее 100 см», «минимум 100 см», «больше/свыше 100 см» и
«Лампа от 4000 K…».

**Требуемое поведение (§2.2).** Одиночная нижняя граница — самостоятельное
условие, независимо от того, как далеко стоит бюджет.

**Минимальная правка (проверена).** Заменить `for/else` на явный флаг; **лимит
`MAX_RANGE_GAP_TOKENS` сохранить** — он нужен, чтобы не склеивать разные условия
(«до 100 ₽, от 3000 до 5000 кельвинов»). Ничего больше в этой функции не менять.

```python
if amount.kind in (LOWER_INC, LOWER_STRICT):
    paired = False
    for other_position in range(position + 1, len(items)):
        ...                                  # тело цикла без изменений
        result.append((amount, other))
        used.update({position, other_position})
        paired = True
        break
    if not paired:                           # ← вместо for/else
        result.append((amount,))
    continue
```

**Приёмка.** Должны стать зелёными 5 тестов
`tests/test_qa_bounds.py::LowerBoundRegressionTest` (снять `skip`) и остаться
зелёными `LowerBoundControlTest` (та же граница работает, когда бюджет назван
без «до»).

**Проверить, что не сломалось:**

```bash
python3 -m unittest tests.test_numbers tests.test_extract tests.test_dialogue
# ожидаемые ответы после правки:
#  «от 100 см … до 15 000 ₽»  → ширины 100, 100, 120 (ни одного «не указана»)
#  «шире 100 см … до 15 000 ₽» → только 110 и 120
#  «от 4000 K … до 15 000 ₽»   → температуры 5000, 5000, 6500 (все ≥ 4000)
```

**Замер (сделан на этой ветке, патчем в памяти, файлы не менялись):** правка
Д1 + Д2 проходит все 383 исходных теста и даёт ожидаемые ответы для всех 7
формулировок нижней границы.

## Д2 (P0, критично). «От 5000 ₽» превращается в потолок бюджета

**Где:** `app/nlp/numbers.py::collect_constraints`, строки 585 и 598:
`budget = max(budget or 0, max(values))`.

**Симптом.** Покупатель, просивший «не дешевле 5 000 ₽», получает самые дешёвые
комплекты, потому что нижняя граница стала верхней:

```bash
echo '{"messages":[{"role":"user","text":"Стол в Таганроге, от 5000 ₽"}]}' \
  | ASSISTANT_OFFLINE=1 ASSISTANT_CACHE_DIR=/tmp/qa python3 -m app.main --catalog data/catalog.json 2>/dev/null
# сейчас: ok, потолок 5000, варианты 2500 / 2700 / 3200
```

**Причина.** В ветке `UNIT_RUB` (и в ветке денежных подсказок) бюджет берётся
как максимум из **всех** значений пары, без учёта вида границы. `LOWER_INC` /
`LOWER_STRICT` ограничивают снизу и потолком быть не могут.

**Требуемое поведение (§3).** Бюджет — общий **верхний** предел; равенство
допустимо. Верхнюю границу бюджета задают только `UPPER_INC`, `UPPER_STRICT`,
`EXACT` и число без триггера (`NO_TRIGGER`, например «бюджет 15000»).
Одиночная нижняя граница в рублях бюджетом **не является** → бюджет остаётся
неизвестным → `clarify` по `budget_rub`. Для пары «от 3000 до 5000 ₽» потолок
по-прежнему 5000.

**Минимальная правка (проверена).**

```python
CAPPING_KINDS = (UPPER_INC, UPPER_STRICT, EXACT, NO_TRIGGER)
caps = [amount.value for amount in pair if amount.kind in CAPPING_KINDS]
if caps:
    budget = max(budget or 0, max(caps))
```

Применить в обеих ветках (рубли и денежные подсказки). Ветки см/К не трогать.

**Приёмка.** Зелёный тест
`tests/test_qa_bounds.py::NumbersTest::test_lower_bound_of_budget_is_not_a_cap`
(снять `skip`): «Стол в Таганроге, от 5000 ₽» → `clarify`, среди `field` есть
`budget_rub`. Дополнительно вручную:

| Запрос | Ожидание |
|---|---|
| «…от 5000 ₽» / «бюджет от 5000» / «от 5000 рублей» | `clarify` по `budget_rub` |
| «…до 15 000 ₽» | `ok`, все суммы ≤ 15 000 |
| «…от 3000 до 5000 ₽» | `ok`, потолок 5 000 |
| «бюджет 15000» / «15 тысяч» | `ok`, потолок 15 000 |
| «Стол в Азове до 2300 ₽» / «до 2299 ₽» | `ok` / `no_match` (граница включительна) |

**Не сломать.** `test_large_budget_number_forms_are_equivalent`,
`test_budget_boundary_is_inclusive`, `test_budget_and_width_in_one_message`,
`test_neutral_number_with_money_hint_is_budget` — все обязаны остаться зелёными
(проверено: проходят).

## Д3 (P1). Из нескольких названных городов используется только последний

**Где:** `app/nlp/extract.py:153` (`city_id = city_hits[-1].value`),
`app/model.py:110` (`Slots.city_id`), `app/catalog/search.py:81`,
`app/catalog/plan.py:52` и `app/catalog/explain.py::explain_no_match`.

**Симптом.** «Стол в Таганроге или в Азове до 5000 ₽» показывает только Азов,
хотя покупатель перечислил оба города как равноправные:

```bash
echo '{"messages":[{"role":"user","text":"Стол в Таганроге или в Азове до 5000 ₽"}]}' \
  | ASSISTANT_OFFLINE=1 ASSISTANT_CACHE_DIR=/tmp/qa python3 -m app.main --catalog data/catalog.json 2>/dev/null
# сейчас: только demo-3-* (Азов); таганрогский стол за 2500 ₽ не показан
```

**Формальная оговорка.** §3 буквально говорит «извлекает … один город», поэтому
формально это не нарушение. Но §2 требует «комплект для самовывоза в одном
городе» (это правило сохраняется), а §4 требует `ok` для выполнимого запроса —
альтернатива через «или» выполнима в двух городах. Поэтому реализуем: **городов
может быть несколько, комплект остаётся в одном городе**.

**Требуемое поведение.**

1. Все упомянутые города собираются в порядке упоминания без повторов.
2. Комплект по-прежнему целиком в одном городе — смешивать города в одном
   варианте запрещено.
3. Ответ собирается по каждому городу; в `options` (1–3 варианта) попадают
   варианты из разных городов так, чтобы каждый названный город был представлен,
   если в нём есть подходящий комплект.
4. `no_match` при отсутствии комплектов ни в одном городе объясняет препятствие
   по всем названным городам (минимумы по каждому), а не только по последнему.
5. «Нет, в Азове» — замена города. «Или в Азове» — добавление альтернативы.
   «Не в Азове, а в Таганроге» — Азов отбрасывается, остаётся Таганрог.
6. Одиночный город работает ровно как раньше.

**Как делать (свобода реализации сохраняется, но контрактные точки — эти).**

* `app/model.py`: добавить в `Slots` поле `city_ids: tuple[str, ...] = ()`.
  `city_id` оставить как «последний явно названный» — на него завязаны тесты
  решения (`tests/test_dialogue.py`: `slots.city_id == "azov"` и др.) и
  `missing_fields`. Хелпер `cities()` → `city_ids or (city_id,)`.
* `app/nlp/extract.py`: собрать все `city_hits`; отбросить упоминания с
  отрицанием перед городом («не в …»); `city_ids` — уникальные по порядку,
  `city_id = city_ids[-1]`. Добавить признак альтернативы
  (`или`/`либо` рядом с перечислением городов, в том числе реплика-продолжение
  «Или в Азове»), по образцу существующего `ADDITIVE_PATTERN`.
  Город вне справочника обрабатывать как сейчас (`city_unknown` → `clarify`).
* `app/nlp/merge.py::merge_step`: при `FIELD_CITY in step.mentioned` —
  признак альтернативы → объединение с прежними `city_ids`; иначе замена.
  Прошлые значения не теряются for «или» и теряются for явной смены.
* `app/catalog/plan.py::build_plan`: обойти города, собрать варианты по каждому
  (не больше 3 на город), затем чередованием (round-robin) сформировать итог не
  длиннее 3 вариантов, убрав дубли по составу ID. Порядок детерминированный.
  `no_match` — когда ни в одном городе комплекта нет.
* `app/catalog/explain.py::explain_no_match`: принимать одно имя или список;
  при нескольких — «ни в Таганроге, ни в Азове …» плюс минимальные суммы по
  каждому городу. Старая сигнатура со строкой должна продолжать работать.

**Приёмка.** Должны стать зелёными 4 теста
`tests/test_qa_history.py::MultipleCitiesTest` (снять `skip`):
оба города представлены; три города представлены; `no_match` упоминает оба
города; «или в Азове» добавляет город.

**Обязательная регрессия (не сломать, уже написано):**

| Тест | Правило |
|---|---|
| `MultipleCitiesTest.test_each_option_is_within_one_city` | вариант не смешивает города |

## Д5 (P2). Технические сбои обязаны быть аккуратными, а не трассировкой

Коды выхода и пустой `stdout` уже соответствуют §1, но в `stderr` при двух
входах падает трассировка Python вместо строки диагностики:

| Вход | Сейчас | Должно быть |
|---|---|---|
| каталог в UTF-16 / не-UTF-8 | код 1 + `UnicodeDecodeError` traceback | код 3 + одна строка «каталог … не удалось прочитать: …» |
| JSON с вложенностью ≥ 100 000 `[` | код 1 + `RecursionError` traceback | код 2 + строка «некорректный JSON: слишком глубокая вложенность» |

**Где:** `app/jsonio.py::load_json_file` (строка 69, `read_text(encoding="utf-8-sig")`)
и `loads_strict`.

**Что сделать:** ловить `UnicodeDecodeError` (подкласс `ValueError`) и
`RecursionError` и превращать в `JsonError` с понятным текстом. Каталог при этом
остаётся `CatalogError` → существующий код выхода 3. `stdout` — пустой.

**Приёмка:** `tests/test_qa_catalog.py::BrokenCatalogTest` (там уже есть случай
«каталог не в UTF-8») остаётся зелёным, трассировок в `stderr` нет:

## Д6 (P2). Схема каталога не проверяется — «мусор» принимается молча

`app/catalog/index.py::parse_listing` проверяет только семь обязательных полей и
типы верхнего уровня. Сейчас принимаются (код 0) данные, которые
`_upstream/schemas/catalog.schema.json` запрещает:

| Данные | Факт | Почему это опасно |
|---|---|---|
| `attributes.width_cm: "90"` | принято, значение считается «неизвестным» | объявление никогда не пройдёт ограничение по ширине — тихая потеря товара |
| `attributes.width_cm: 0` | принято | схема требует целое ≥ 1 |
| `attributes: {"a": {"b": 1}}`, `{"a": [1]}`, `{"a": null}` | принято | схема разрешает только string / number / boolean |
| `attributes.adjustable_height: "true"` | принято как «неизвестно» | то же |
| `city_id: "unknown-city"` | принято | схема требует `enum` из `data/cities.json` |

**Требование.** Каталог приходит от организаторов и соответствует схеме
(§1: «Проверочный каталог имеет ту же схему»). Поэтому нарушение схемы —
техническая ошибка каталога (`CatalogError`, код 3, пустой `stdout`), а не
повод молча выдать неверный подбор.

**Что сделать в `parse_listing`:**

* `attributes`: каждое значение — `str`, `int`/`float` (не `bool`) или `bool`;
  вложенные объекты, массивы и `null` → `CatalogError`;
* для документированных ключей — типы и границы из схемы:
  `width_cm` и `color_temperature_k` — целое ≥ 1, `adjustable_height` — `bool`;
  ключи чувствительны к регистру, лишние ключи разрешены (§2.3);
* `city_id` — из `data/cities.json` (справочник уже читает
  `app/catalog/plan.py::city_names`; используйте его, не дублируйте список).

**Не переусердствовать:** не требовать `minItems`, не запрещать пустой
`attributes: {}`, не ограничивать число дополнительных ключей, не проверять
`description` на непустоту.

1. **Д1** → прогнать `tests.test_numbers tests.test_extract tests.test_dialogue`
   → снять 5 `skip` в `LowerBoundRegressionTest` → прогнать
   `tests.test_qa_bounds`.

   `tests.test_qa_bounds` целиком.

4. **Д4–Д6** → прогнать `tests.test_qa_catalog`, `tests.test_index`, `tests.test_io`.

   `OK (skipped=2)` (остаются только два исходных skip репозитория); отдельно
   убедиться, что `grep -rn "@unittest.skip" tests/test_qa_*.py` пуст.

   запросов без модели должна остаться ≥ 60 % (сейчас 89 %), p50 — доли

осталось.

## Формат сдачи

На каждый дефект:

* файлы и строки, которые изменены, и почему именно так;
* команда воспроизведения «до» и «после» (из `docs/QA-ERRORS.md`);
* какие `skip` сняты и вывод прогона;
* подтверждение, что публичный контракт не изменился:
  `git diff HEAD -- app/contract/ _upstream/ data/` — пусто.

Запрещено: подгонять тесты под текущее поведение, глушить assert, расширять
`response.schema.json`, добавлять поля в ответ, менять коды выхода, коммитить
ключи `LLM_*` и `.env`.
