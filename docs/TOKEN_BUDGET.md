# Бюджет токенов (§5)

Требование кейса: модель используется **там, где она нужна**, каталог в неё не
передаётся, и большинство запросов обслуживается без единого токена. Ниже —
как это устроено, чем измерено и что именно можно предъявить комиссии.

Все числа получены на каталоге организаторов (111 объявлений) командой
`python bench/load.py` и одним живым вызовом шлюза; воспроизводится одной
командой (см. конец документа).

---

## 1. Куда вообще могут уйти токены

В системе ровно **одно** место, где есть сеть: `app/llm/client.py`. Оно умеет
одну операцию — «реплика покупателя → JSON с условиями» — и вызывается из
`merge.resolve_missing`. Всё остальное считается локально:

| Шаг | Токены | Где считается |
|---|---:|---|
| чтение и разбор каталога | **0** | `app/catalog/index.py` |
| индекс, сортировки, кэш на диске | **0** | `app/catalog/index.py` |
| разбор реплики (город, категории, числа, границы, флаг) | **0** | `app/nlp/*` |
| кэш разборов по `sha256` реплики | **0** | `app/nlp/cache.py` |
| подбор комплектов (DFS + отсечение) | **0** | `app/catalog/search.py` |
| объяснения и `no_match` | **0** | `app/catalog/explain.py` |
| **извлечение недопонятых условий моделью** | 251 | `app/llm/client.py` |

Ключевое архитектурное решение: **каталог в модель не передаётся ни при каких
условиях**. В запросе ровно два сообщения — сжатый системный промпт и текст
реплики. Поэтому:

* расход не зависит от размера каталога (111 или 250 объявлений — одинаково);
* текст объявления физически не может попасть в контекст модели, а значит и
  повлиять на ответ через промпт-инъекцию (см. §9 и `docs/ALGORITHMS.md`);
* схема ответа маленькая, поэтому и выход короткий.

## 2. Измеренный обмен одного вызова

Живой вызов шлюза организаторов, реплика
«Хочу обставить кабинет: стол, кресло и лампа. Таганрог, тысяч пятнадцать на всё»:

```
[buyer-assistant] модель: prompt=197 completion=54 total=251
ответ модели за 5460 мс: {"city_id": "taganrog", "budget_rub": 15000, "categories": ["table", "chair", "lamp"]}
```

| Параметр | Значение | Комментарий |
|---|---:|---|
| `prompt_tokens` | **197** | системный промпт (821 байт) + схема (317 байт) + реплика |
| `completion_tokens` | **54** | три поля JSON, без пояснений |
| `total_tokens` | **251** | один обмен на один запрос |
| наш `max_tokens` | **200** | контракт разрешает 2000 — берём в 10 раз меньше |
| задержка шлюза | 5,5 с | укладывается в 120 с с большим запасом |

Почему `max_tokens=200`, а не 2000: ответ — объект из трёх полей. Просить 2000
токенов значит разрешить модели «порассуждать» и потратить квоту впустую.
Схема `strict` + `additionalProperties: false` не даёт вернуть лишние поля.

Что **не** входит в схему и почему: ширина стола, температура лампы и
регулировка кресла извлекаются локально из чисел и единиц
(`app/nlp/numbers.py`). Меньше полей — короче выход и меньше способов «выдумать»
ограничение, которого покупатель не называл.

## 3. Когда модель не вызывается вообще

Решение принимается **после** слияния всей истории диалога
(`merge.merge_history` → `merge.resolve_missing`), а не по одной реплике:

1. реплика разбирается лексиконом — 0 токенов;
2. если после всех реплик `city_id`, `budget_rub` и `categories` известны —
   вызова нет;
3. если модель **физически не может** закрыть недостающее (`model_can_help`:
   бюджет не назван или город не к чему привязать) — вызова тоже нет: значение
   пришлось бы выдумать, а ответ всё равно остался бы `clarify`;
4. иначе — **один** вызов на запрос, в который уходит весь диалог одним куском;
5. повторная формулировка обслуживается кэшем разборов — снова 0 токенов.

Пример из демонстрации: диалог

```
покупатель: Стол в Таганроге.
помощник:   Какой у вас бюджет на весь комплект?
покупатель: 12 тысяч.
```

стоит **0 токенов**, хотя ни одна реплика по отдельности всех условий не
содержит. До правки этого правила модель вызывалась дважды (по разу на реплику):
именно стенд `bench/load.py` показал лишние вызовы, и они были убраны.

## 4. Замер: 89 % запросов без модели

Стенд прогоняет смесь из девяти типовых запросов (выбор, уточнение, `no_match`,
диалог, «лексикон не понял») по кругу и считает **фактические** обращения к
модели, подменяя её функцией-счётчиком:

```
$ python bench/load.py
каталог: 111 объявлений, 9 пар (город, категория), дайджест 3a00b6db9e1c
индекс: холодная сборка 0.52 мс, чтение из кэша 1.40 мс (from_cache=True)

холодный кэш разборов: n=200, p50=0.04 мс, p95=0.89 мс, p99=2.19 мс, 4693 запр/с, модель=22
прогретый кэш разборов: n=200, p50=0.03 мс, p95=0.34 мс, p99=0.57 мс, 7407 запр/с, модель=22
    вызовов модели на один запрос по рецептам:
      выбор-01               0 токенов (лексикон)
      выбор-02               0 токенов (лексикон)
      выбор-03               0 токенов (лексикон)
      уточнение-город        0 токенов (лексикон)
      уточнение-бюджет       0 токенов (лексикон)
      нет-вариантов          0 токенов (лексикон)
      диалог                 0 токенов (лексикон)
      нужна-модель           1 вызов модели
      пустая-реплика         0 токенов (лексикон)
полный ./run: p50=166 мс, p95=172 мс, max=172 мс, коды выхода [0]

Бюджет токенов §5 (измеренный обмен: prompt=197, completion=54)
холодный кэш: запросов 200, без модели 178 (89%), потрачено ≈5522 ток., сэкономлено ≈44678 (89%)
прогретый кэш: запросов 200, без модели 178 (89%), потрачено ≈5522 ток., сэкономлено ≈44678 (89%)
```

Как читать эти числа честно:

* **89 %** запросов обходятся без модели. Это выше цели §5 (60 %) — и выше
  прежних 62 %, потому что вызов теперь не делается там, где он заведомо пуст:
  без названного бюджета или без привязки к городу модель могла бы только
  выдумать значение (гейт `extract.model_can_help`).
* Оставшиеся 11 % — запросы, где **есть материал для модели**: город и бюджет
  названы, а предмет описан словами («деревяшка с четырьмя ножками, Таганрог,
  до 15 000»). Ровно там вызов превращает `clarify` в `ok`.
* «Сэкономлено ≈44 678 токенов» — сравнение с подходом «каждую реплику отдаём
  модели» на том же наборе (200 запросов × 251 токен). Это не абсолютная
  экономия, а разница стратегий; формула лежит в `bench/load.py::token_report`.
* Задержки подбора — **доли миллисекунды**: 0,04 мс p50 на холодном кэше и
  0,03 мс на прогретом. Полный `./run` (старт интерпретатора + каталог + ответ)
  — 166 мс p50 при лимите 120 с. То есть узкое место — только сеть модели, и
  именно поэтому её вызовы сведены к одному на запрос.

## 5. Лимиты шлюза: что проверяется до отправки

`LLM_API.md` ограничивает один вызов. Всё это проверяется **локально, до сети**
(`llm.client.build_payload`), чтобы не тратить квоту на заведомо отклонённый
запрос:

| Лимит шлюза | Наш контроль | Где |
|---|---|---|
| тело ≤ 65 536 байт | проверка `len(data)` | `build_payload` |
| вход ≤ 32 768 байт | сумма байтов всех `content` | `build_payload` |
| выход ≤ 2000 токенов | просим 200 | `LLM_MAX_OUTPUT_TOKENS` |
| ≤ 40 сообщений | отправляем 2 | `make_resolver` |
| схема ≤ 16 384 байт | 317 байт | `build_payload` |
| 20 rpm / 2 параллельно | один запрос на процесс | архитектура |
| 90 с на ответ | `min(90, остаток дедлайна)` | `complete` |
| редиректы | запрещены (`_NoRedirect`) | `complete` |

Про 20 rpm: один запуск `./run` — один процесс и максимум один вызов модели,
поэтому параллельность и частоту мы не превышаем по построению. Ретраев почти
нет: единственная повторная попытка — после `429`, и только если пауза из
`Retry-After` помещается в оставшийся бюджет запуска.

## 6. Что происходит при сбое модели

Сбой модели — **техническая** ошибка, а не «нет вариантов»:

| Ситуация | Ответ | Код |
|---|---|---|
| 401/403 (ключ, `error code: 1010`) | stderr с причиной и подсказкой | 5 |
| 429 дважды | stderr `rate_limited` | 5 |
| 502/503 | stderr `upstream` | 5 |
| не-JSON / нет `choices` | stderr `non_json` / `protocol` | 5 |
| исчерпан бюджет времени | stderr `deadline`, запрос **не отправлен** | 5 |

`no_match` в этих случаях не используется никогда (CONTRACT.md §1): «нет
подходящих комплектов» — это утверждение о каталоге, а не о состоянии сети.
Точно так же мы не отдаём «уточните город»: это перекладывало бы нашу аварию на
покупателя.

Если модель недоступна **штатно** (`ASSISTANT_OFFLINE=1` или нет ключа), система
работает полностью: разбор идёт лексиконом, ответ остаётся корректным, просто
реплики вроде «Хочу обставить кабинет» приводят к `clarify`. Именно в этом
режиме работает вся автопроверка и все 300+ тестов — сеть им не нужна.

## 7. Как воспроизвести

```sh
python bench/load.py                 # 200 запросов в процессе + 5 полных ./run
python bench/load.py --requests 500  # больше замеров
python bench/load.py --json          # метрики в JSON (для отчёта)
```

Стенд **не ходит в сеть**: модель подменяется счётчиком, поэтому квота
организаторов не расходуется и прогон можно повторять сколько угодно раз.
Живой обмен (197/54) измеряется отдельно, одним вызовом с реальным ключом из
`.env`; число зафиксировано в константах `bench/load.py` и в этом документе.
